## Question 1: OAuth Fundamentals
> **Explain Client ID, Client Secret, Access Token, and Refresh Token, and how they are used in an API integration.**

### 1. Short Answer
- **Client ID**: The public identifier for your application registered in Zoho API Console.
- **Client Secret**: The confidential secret key known only to your application server and Zoho used to authenticate your application during token exchanges.
- **Access Token**: A short-lived credential (typically 1 hour) included in API request headers (`Authorization: Zoho-oauthtoken <token>`) to authorize CRM operations.
- **Refresh Token**: A long-lived credential used to obtain new access tokens silently without prompting the user to log in again.

### 2. Detailed Technical Explanation
In an OAuth 2.0 Authorization Code flow:
1. The user is redirected to Zoho’s OAuth server (`/oauth/v2/auth`) with `client_id`, `redirect_uri`, `scope`, `response_type=code`, and `access_type=offline`.
2. After user consent, Zoho redirects back to `redirect_uri` with a one-time, short-lived **Authorization Code** (valid ~2-10 minutes).
3. The backend server makes a back-channel POST request to Zoho (`/oauth/v2/token`) providing the `code`, `client_id`, and `client_secret`.
4. Zoho validates the secret and authorization code, issuing an **Access Token** and **Refresh Token**.
5. The backend stores the refresh token securely and uses the access token in HTTP headers for CRM API requests.

### 3. Likely Follow-up Questions & Answers
- **Q: Why shouldn't the Client Secret or Refresh Token be stored on a single-page app (SPA) or mobile app?**  
  *Answer:* SPAs and mobile apps run in public, client-controlled environments where source code and network storage can be inspected. If a refresh token or secret is exposed, an attacker could impersonate the app indefinitely. Public clients should use OAuth 2.0 with PKCE (Proof Key for Code Exchange) or a backend proxy (BFF - Backend For Frontend).
- **Q: What is the purpose of the `state` parameter during authorization?**  
  *Answer:* CSRF protection. A cryptographically random string generated by our server is sent with the auth request and validated when Zoho redirects back, preventing attackers from injecting their own authorization codes into a victim's session.

### 4. Code Location
- Authorization URL & Exchange: [`src/services/zoho-auth.service.ts`](file:///src/services/zoho-auth.service.ts)
- Token Persistence: [`src/services/zoho-token-store.service.ts`](file:///src/services/zoho-token-store.service.ts)

## Question 2: Token Expiration Handling
> **Your application works today but tomorrow returns an authentication error. What could cause this? How would you avoid asking the user to authorize every time?**

### 1. Short Answer
Zoho CRM access tokens have a fixed lifespan of **1 hour (3600 seconds)**. The next day, the access token is expired, causing Zoho to return `401 Unauthorized` / `INVALID_TOKEN`. To avoid re-prompting the user, the application uses the long-lived **Refresh Token** to silently request a new access token via an automated background refresh mechanism.

### 2. Detailed Technical Explanation
In our implementation:
1. When authorizing initially, we request `access_type=offline` and `prompt=consent` to ensure a `refresh_token` is generated.
2. We persist the refresh token in our token store.
3. Our HTTP client ([`ZohoCrmService`](file:///src/services/zoho-crm.service.ts)) employs an **Axios Response Interceptor**:
   - When an API call returns `401` or `{ code: "INVALID_TOKEN" }`, the interceptor catches the error.
   - It acquires a mutex/lock (`isRefreshing = true`) to prevent race conditions from concurrent requests.
   - It calls Zoho Accounts endpoint with `grant_type=refresh_token`.
   - It stores the newly issued access token with updated expiration time.
   - It retries the original request with the new access token header.
   - Any other concurrent requests are queued and resolved once the token is refreshed.

### 3. Common Mistakes to Avoid
- Storing access tokens in global variables without persistence, causing loss upon server restart.
- Not implementing a retry guard (`_retry = true`), causing infinite retry loops if the refresh token itself is revoked.
- Triggering multiple simultaneous refresh requests when 10 API calls fail at the same second instead of queuing them.

## Question 3: API Field Names vs Display Labels
> **A CRM field is displayed as "Customer Type" but the API expects "Customer_Type". Why does this matter? How would you find the correct API field name?**

### 1. Short Answer
CRM UI display labels are localized and customizable for human readability, whereas the API requires the immutable database-level API identifier (`api_name`). Using the display label causes Zoho to ignore the field or return a `400 / INVALID_DATA` error. API names can be found via the Zoho CRM Field Metadata API (`GET /crm/v8/settings/fields?module=Leads`) or in **Setup → Customization → Modules and Fields → Fields → API Names**.

### 2. Detailed Technical Explanation
- Display labels can contain spaces, special characters, and change dynamically across languages (e.g. English vs Spanish).
- The Zoho CRM database schema references fields via internal snake_case identifiers (e.g., `First_Name`, `Lead_Source`, `Annual_Revenue`).
- In our application, we maintain a dedicated mapping layer in [`LeadService.createLead()`](file:///src/services/lead.service.ts) and [`LeadService.mapZohoLeadToDTO()`](file:///src/services/lead.service.ts) to decouple internal camelCase DTOs (`firstName`, `leadStatus`) from Zoho's `First_Name` and `Lead_Status`.

## Question 4: Inserting a Lead via HTTP API
> **Explain how you would insert a Lead using an HTTP API. Cover HTTP method, URL structure, authorization, request body, required fields, and expected response.**

### 1. Comprehensive Breakdown
- **HTTP Method**: `POST`
- **URL Structure**: `https://www.zohoapis.com/crm/v8/Leads` (or region-specific domain, e.g. `.eu`, `.in`).
- **Authorization Header**: `Authorization: Zoho-oauthtoken <ACCESS_TOKEN>`
- **Request Headers**: `Content-Type: application/json`
- **Required Fields**: In Zoho CRM Leads, `Last_Name` is mandatory by default (and `Company` in standard B2B configurations).
- **Request Body**:
```json
{
  "data": [
    {
      "First_Name": "John",
      "Last_Name": "Smith",
      "Company": "ABC Ltd",
      "Email": "john.smith@example.com",
      "Phone": "+8801700000000",
      "Lead_Status": "Not Contacted"
    }
  ],
  "trigger": ["approval", "workflow", "blueprint"]
}
```
- **Expected Success Response (`201 Created` / `200 OK`)**:
```json
{
  "data": [
    {
      "code": "SUCCESS",
      "details": {
        "id": "716492000000382001",
        "Created_Time": "2026-09-26T10:00:00+06:00",
        "Created_By": { "id": "716492000000045001", "name": "Admin" }
      },
      "message": "record added",
      "status": "success"
    }
  ]
}
```

## Question 5: GET Records vs Searching Records
> **What is the difference between retrieving records and searching records? Give an example of when you would use each.**

### 1. Key Differences
| Attribute | GET Records (`/crm/v8/Leads`) | Search Records (`/crm/v8/Leads/search`) |
|---|---|---|
| **Purpose** | Bulk retrieval, listing, or table pagination | Targeted lookup by specific criteria (email, phone, word) |
| **Filtering** | Limited (supports `page`, `per_page`, `sort_by`, `fields`) | Advanced criteria (`(Email:equals:x@y.com)` or `word=John`) |
| **Response on Empty** | Returns `{ data: [], info: ... }` | Returns `204 No Content` or empty data array |
| **Performance** | Optimized for scanning indexed sequential pages | Optimized for index-based criteria lookup |

### 2. Practical Use Cases
- **Use `GET /Leads`**: Displaying a paginated directory of contacts in a CRM dashboard or syncing bulk updates to a data warehouse.
- **Use `GET /Leads/search`**: Checking for duplicates prior to inserting a new signup form submission (`?email=user@test.com`) or looking up a caller's record by phone number in a CTI integration.

## Question 6: Duplicate Prevention
> **Your application receives the same customer twice. How would you prevent duplicate CRM records?**

### 1. Implementation in this Project
1. **Pre-flight Search**: In [`LeadService.createLead()`](file:///src/services/lead.service.ts), we query `GET /crm/v8/Leads/search?email=${dto.email}` before creating the record.
2. **Conflict Response**: If a match is found, we halt execution and return HTTP `409 Conflict` containing the existing Zoho Record ID and metadata.
3. **Zoho Native Upsert / Duplicate Check**: Alternatively, Zoho API v8 supports the `duplicate_check_fields` parameter (`duplicate_check_fields: ["Email"]`), which instructs Zoho's engine to update existing or reject duplicates atomically.

### 2. Limitations of Email Matching & Business Considerations
- **Shared Inboxes**: Multiple agents or family members might use `contact@business.com` or `info@domain.com`.
- **Typo / Sub-domains**: `john@corp.com` vs `john@us.corp.com`.
- **Composite Key Matching**: Real-world business requirements often combine `Normalized Phone Number + Cleaned Company Name + Country Code` to ensure accurate identity resolution.

## Question 7: HTTP 401 / OAUTH_SCOPE_MISMATCH
> **The API returns HTTP 401 / OAUTH_SCOPE_MISMATCH. What does it mean? How would you investigate and fix it?**

### 1. Meaning
`OAUTH_SCOPE_MISMATCH` indicates that the access token provided in the `Authorization` header is valid, but was issued without the required permissions (scopes) to access the requested module or endpoint (e.g. attempting to create a Lead when only `ZohoCRM.users.READ` was authorized).

### 2. Investigation & Remediation Steps
1. **Identify Missing Scopes**: Compare the endpoint requirement (`ZohoCRM.modules.ALL` or `ZohoCRM.modules.leads.CREATE`) with scopes configured in `.env` (`ZOHO_SCOPES`).
2. **Update Scope Configuration**: Ensure `ZohoCRM.modules.ALL` and `ZohoCRM.settings.ALL` are requested.
3. **Re-Initiate Consent Screen**: Generate a new authorization URL with `prompt=consent` (`GET /auth/zoho`).
4. **Re-Authorize**: Have the account administrator grant permissions on the Zoho consent prompt.
5. **Exchange Code**: Obtain a new Refresh Token possessing the updated scope set.

## Question 8: Multi-Tenant Production Architecture
> **A Node.js application connects to multiple clients' CRM accounts. How would you store OAuth credentials securely and keep each customer's data isolated?**

### 1. Architecture Design
```
Incoming Request ──> [Tenant Context Middleware (Extract tenant_id from JWT)]
                                  │
                                  ▼
                     [Encrypted Token Store (Redis / DB)]
                        Key: tenant:{tenant_id}:zoho_tokens
                                  │
                                  ▼
                      [ZohoCrmService Instance / Request Context]
                        Header: Authorization: Zoho-oauthtoken <tenant_access_token>
```

### 2. Security & Isolation Principles
1. **Isolated Keying**: Tokens are never stored globally. Every token record is indexed by `tenant_id`.
2. **Encryption at Rest**: `refresh_token` and `client_secret` are encrypted using AES-256-GCM with envelope encryption via AWS KMS or HashiCorp Vault before saving to the database.
3. **Row-Level Security (RLS)**: In PostgreSQL, database tables enforce RLS ensuring queries cannot cross tenant boundaries.
4. **Credential Isolation**: Support custom `client_id` and `client_secret` per enterprise tenant if they bring their own Zoho API Console developer account.

## Question 9: Synchronizing 200,000 CRM Records
> **A client needs 200,000 CRM records synchronized with an external system. Explain pagination, batching, rate limits, retries, failed records, logging, and resume/retry design.**

### 1. Comprehensive Architecture Plan
1. **Bulk API vs REST API**:
   - For 200k records, prefer the **Zoho Bulk Read API v2**, which asynchronously exports CSV files in compressed format, consuming only 1 API credit instead of 1,000 paginated requests.
   - For real-time sync, use paginated REST API with `per_page=200` (requires 1,000 API requests).
2. **Rate Limit & Concurrency Management**:
   - Zoho enforces concurrency limits (e.g. 10 concurrent requests) and daily call limits.
   - Use a distributed queue (BullMQ / Redis) with rate limiting (e.g. 5 requests/second max).
3. **Resumable State & Watermarking**:
   - Persist a sync checkpoint: `last_synced_modified_time` or `page_cursor` in database/Redis.
   - If the worker crashes at record 142,000, it resumes from the recorded cursor without reprocessing the first 141,999.
4. **Exponential Backoff & Retries**:
   - For `429 Too Many Requests` or `503 Service Unavailable`: apply jittered exponential backoff: `delay = min(30000, 1000 * 2^attempt + random(100, 500))`.
5. **Dead Letter Queue (DLQ)**:
   - Records failing validation or foreign key constraints are pushed to a `failed_records` table with the raw payload, error code, and timestamp for manual inspection or bulk replay.
6. **Auditing & Metrics**:
   - Log batch progress metrics (processed, succeeded, failed, throughput) with zero sensitive PII logging.

## Question 10: W3SCLOUD Webhook / Ingestion Scenario
> **Design External Website → Node.js API → Zoho CRM for this payload: `{ name: 'John Smith', email: 'john@example.com', company: 'ABC Ltd', phone: '+8801XXXXXXXXX' }`.**

### 1. End-to-End Flow Diagram
```
[External Website Form]
         │ (HTTPS POST /webhook/lead)
         ▼
[Node.js / Express Gateway]
         │
         ├─── 1. Rate Limiting (express-rate-limit: 10 req/min per IP)
         ├─── 2. HMAC Signature Verification (X-Signature header check)
         ├─── 3. Zod Payload Validation (Splits 'name' -> 'firstName', 'lastName')
         │
         ▼
[Message Queue (BullMQ / Redis)] ──> Returns HTTP 202 Accepted to Webhook
         │
         ▼
[Background Worker Consumer]
         │
         ├─── 4. Duplicate Check (Search Zoho by Email / Phone)
         ├─── 5. Field Mapping (CamelCase -> Zoho API Field Names)
         ├─── 6. Execute POST /crm/v8/Leads via ZohoCrmService
         ├─── 7. Auto-Retry with Exponential Backoff on Zoho outage
         └─── 8. Structured Logging & Metrics
```

### 2. Resilience During Zoho CRM Outages
- Because the ingestion gateway acknowledges the website immediately with `202 Accepted` after enqueueing in Redis, website users experience zero downtime even if Zoho CRM is undergoing scheduled maintenance.
- The background workers hold the jobs in queue, retrying automatically until Zoho service restoration.
